## 总体设计

### 命令组织方式

使用类似 `kubectl` 这种动词优先的形式，紧跟的参数表示行为比如 `get` `describe`，还是类似 `docker` 这种名词优先的形式，紧跟的参数表示不同实体或者模块的比如 `image` `container` 的方式？

似乎 Crater 更适合后者，每个模块都是单独设计的，比较难抽象出统一的行为。

名词优先也更 AI 友好，可以在相应的域中使用 `help` 和 Tab 键查看受支持的命令。

### 错误处理

目前状态：`cmd/root.go` 负责最终输出，但错误在各命令里分散封装；API 层也多返回普通 `error`，导致错误信息不稳定、重复逻辑多，且后端响应细节容易丢失。

收敛目标：无论是脚本/AI 还是人类用户，错误都先被统一成同一种“结构化错误对象”（包含 `category/code/message/context`），再根据输出模式渲染为 JSON 或人类可读文本；接口响应结构变化时，也能尽量保留后端原始信息用于诊断与兼容。

推荐边界：

- **API 层负责**：把非成功响应统一包装为 `CLIError`，并在 `Context` 中附带 `http_status`、`backend_raw`（必要时再补 `backend_json`）。
- **统一错误码**：用 CLI 自己的错误码表达失败类型（如 `ERR_UNAUTHORIZED` / `ERR_SERVER_INTERNAL` / `ERR_NETWORK_FAILURE`）。
- **命令层负责**：只处理缺参、交互取消、本地状态等“纯本地错误”，不重复写 HTTP 错误翻译逻辑；同时允许命令按需注册/配置自己的错误翻译与增强逻辑（例如给出更明确的下一步操作）。

渲染层（统一出口）只做两件事：`--json` 下输出稳定的错误 JSON；否则输出分行、缩进、带必要上下文与建议的人类可读文本。

## 构建和分发

### 编程语言

用什么编程语言呢？

- **Go**：编译成单一二进制，零依赖，交叉编译一条命令搞定，性能好启动快，CLI 生态成熟（Cobra/Viper），学习曲线平缓。
- **Rust**：单二进制零依赖，性能极致，CLI 标杆工具多（ripgrep、fd 等），类型安全但学习曲线陡，编译时间长，二进制体积比 Go 大。
- **TypeScript/Node.js**：与前端同语言可复用类型定义，npm 生态丰富，但需用户先装 Node 运行时，打包后体积大（几十 MB）。
- **Python**：熟悉度高，CLI 生态好（click、tyter），但需 Python 运行时，打包成可执行文件体验不佳，对 macOS 用户不友好（默认无 Python）。

得益于一堆现成的 TUI 组件库，TS 在现在的 TUI 程序比如 Claude Code、OpenCode 中使用非常广泛，但是并不完全适合 Crater CLI，我们没有那么复杂的前端交互需求，甚至对于我们的场景来说这是负优化，不如 Go 的单一可执行文件更能让用户省心。

目前倾向于使用 Go，保持开发使用的版本和后端版本完全一致。

### 构建和分发

主要有 macOS、Linux 和 Windows 用户，如何分发这个 CLI 工具呢？

- **Homebrew Tap**：在组织下创建 `homebrew-tap` 仓库，开发者在主仓库发版时通过 CI 自动更新 Tap 中的 Formula。面向 macOS/Linux 开发者，用户通过 `brew tap crater-project/tap` 关联后即可 `brew install/upgrade`。
- **npm/npx**：发布到 npm 仓库（包名可为 `crater-cli`），开发者需维护 `package.json` 并通过 `postinstall` 自动下载对应平台的二进制。面向 AI Agent 和前端开发者，用户无需安装即可通过 `npx crater` 运行。

### 版本管理和兼容性

CLI 工具需要用到 API，但是 API 可能会随着 Crater 迭代，但是总不能让用户频繁的更新这个命令行工具，因此如何处理版本兼容性的问题呢？

- **API 版本化**：后端 API 采用 `/v1` 等路径，严格保证向后兼容，禁止在现有路径上进行破坏性变更。
- **能力协商**：CLI 启动时通过 `/version` 接口检查后端能力，针对不支持的新功能提供优雅的降级提示。
- **平滑升级**：内置 `crater upgrade` 命令，当检测到版本落后或 API 强制要求更新（如 `426 Upgrade Required`）时，引导用户一键升级。

> [!IMPORTANT]
> **进行中的重构影响**：目前正在进行一次前后端接口结构的深度重构，虽然短期不影响功能，但由于重构周期长且涉及核心数据结构，将对 CLI 的接口调用模型产生深远影响。目前暂不进行最终技术决策，需持续观察重构进展以确定 CLI 的适配策略。

## 状态管理

### 鉴权与 token 保存方式

登录完成之后把 token 保存在 `~/.crater` 之类的目录？现有的工具是怎么做的？Windows 上又要如何处理。

- **跨平台路径规范**：使用 `adrg/xdg` 库自动适配。macOS/Linux 遵循 XDG 规范（`~/.config/crater/`），Windows 适配 `%APPDATA%\crater\`。
- **安全存储选型**：集成 `99designs/keyring`。优先使用系统级密钥库（macOS Keychain / Windows Credential Manager），仅在不可用时降级为受限权限 (`0600`) 的本地文件存储。
- **Token 隔离**：凭证（Token）与普通配置/缓存分离存储，确保敏感数据受到操作系统层级的保护。

### 用户数据缓存

Crater 的登录接口在登陆成功时会返回不少用户的信息，前端会把它放到浏览器缓存中，在 CLI 中应该怎么做？和 token 一起存储吗？

- **上下文（Context）绑定**：Crater 后端将 AccountID 编码于 JWT Token 中。CLI 切换账户本质是调用 `/auth/switch` 换取绑定了新账户上下文的 Token 并覆盖本地存储。
- **持久化策略**：在 `state.json` 中缓存 Token 解析出的 `UserProfile`（用户名、角色、所属组织列表等）和当前选中的 `AccountName`。
- **请求简化**：由于 Token 已承载核心上下文，CLI 请求时无需额外 Header，仅需在 `state.json` 中维护当前 UI 显示所需的账户名称。
- **缓存更新**：采用“本地优先”策略，仅在执行 `crater auth` 相关命令或 API 返回 `401/403` 时强制刷新用户信息，提高响应速度并减少 API 负载。

## 网络

### API URL 结构问题

现在是不是在用户指定的 `platform` 之后添加了一些 API 前缀？生产环境的 API URL 结构和测试环境是否是不同的，是否应该允许进行配置？

目前后端的 API bath path 是固定的，并不会因为生产/测试环境就发生变化，但最好还是把相应的部分抽离出来允许配置，至少让代码改起来比较方便。

推荐将 CLI 中散落在各个 API 调用函数里的 URL 路径抽离为常量（或路径表），并按“前缀 + 资源路径”的方式分层组织，避免重复与不一致。

- **前缀常量（版本/模块级）**：只表达稳定的 base path 结构，便于未来整体迁移或按环境覆盖。
  - `AuthPrefix = "/api/auth"`
  - `V1Prefix = "/api/v1"`
- **资源路径常量（拼接前缀）**：只表达资源名与操作，避免在业务函数里散落字符串。
  - `AuthLoginPath = AuthPrefix + "/login"`
  - `VCJobsPath = V1Prefix + "/vcjobs"`
  - `VCJobsAllPath = V1Prefix + "/vcjobs/all"`
  - `VCJobsJupyterPath = V1Prefix + "/vcjobs/jupyter"`
  - `VCJobsSSHPathFmt = V1Prefix + "/vcjobs/%s/ssh"`
- **落地位置（建议）**：集中放在 `cli/internal/api/paths.go`（或 `endpoints.go`），让 `client.go` 专注于请求与序列化/反序列化，路由字符串由单文件维护。

这样做的直接收益是：当后端前缀发生变化（例如 `/api/v1` -> `/api/v2`）或引入“发现机制/可配置 base path”时，只需修改少量常量即可完成迁移。而且还可以与自动化测试的设计和解耦方案有结合。

### 代理问题

目前的命令行工具如何使用和配置代理？集群在内网环境可能需要使用 VPN 访问。用户主机上可能有不同的 VPN 软件，如何确保用户使用的是正确的？

暂时不处理这个问题，`net/http` 应该能继承系统行为，目前的 CLI 工具能够正常通过 VPN 访问。

## 测试

### 如何自动化测试

实际运行的后端无法通过公网访问，如何进行自动化测试？或者仅仅先简单测试命令解析和参数处理而不测试实际的 API 请求？

一方面希望引入一些自动化测试机制，另一方面哪怕不自动化，手动的跑一些覆盖比较全的脚本把输出记录下来也行，至少能作为 review 的参考。

- **分层测试策略**：将测试分为“指令解析与逻辑”和“API 通信”两个层次。
- **依赖注入与解耦 (Dependency Injection)**：在 `cmd/` 命令定义中，严禁硬编码 `api.NewClient`。通过引入 `APIClient` 接口，在运行时根据环境注入真实的 Client 或测试用的 MockClient。
- **Mock 机制**：利用 MockClient 在内存中模拟后端返回的各种 JSON 响应（成功、401、500 等），从而在 1ms 内验证 CLI 在各种边界条件下的逻辑分支（如 Token 存储、配置更新、错误码映射）。
- **指令仿真 (Cobra Testing)**：利用 Cobra 提供的 `SetArgs` 和 `SetOut/SetErr` 重定向能力，在单元测试中捕获命令行的输出并进行断言，验证 `--json` 和 `--no-interactive` 等全局参数的执行效果。
- **声明式快照测试 (Declarative Snapshot Testing)**：为了直观验证命令在不同参数下的行为，采用“声明输入 -> 录制输出”的快照模式。
  - **多格式支持**：快照文件同时记录 Stdout 和 Stderr 的原始文本，无论是人类可读的表格还是机器可读的 JSON，均可通过 Git Diff 进行直观对比。
  - **低维护成本**：通过 `scenarios.yaml` 声明测试矩阵，测试框架自动发现并运行所有案例，无需为每个子命令手写测试逻辑。
  - **AI 协同**：由 AI 根据 `COMMANDS.md` 契约自动生成测试场景初稿，开发者通过审核生成的快照文件（Golden Files）来确认逻辑实现是否符合预期。
- **与 API URL 抽离的结合点**：将 API 路径从业务函数中抽离为 `Endpoints/Paths`（例如 `AuthPrefix`、`V1Prefix` 与各资源路径常量），并将其作为可替换依赖的一部分。
  - **双层可注入**：`cmd/` 层注入 `APIClient`（控制“是否真的发网络请求”），`api/` 层注入 `Endpoints`（控制“请求打到哪里”）。
  - **测试更稳**：MockClient 不需要关心路径拼接细节；同时可以单测路径表的拼接规则，避免出现 `/api/api/...` 这类错误。
  - **环境适配更容易**：未来如果引入 “discovery / 可配置 base path”，只需替换 `Endpoints` 生成逻辑即可，不需要改动业务命令或 API 调用代码。
- **优势**：实现了 100% 的网络脱钩，确保测试在任何环境下（如无公网的 CI 容器）都能极速、稳定地运行，且对 AI 编写和维护测试极其友好。

### Skills 的分发

如何让 AI Agent 快速获得操作该 CLI 的能力？传统的克隆仓库方式过于繁重。

### 禁用交互式模式

很多 AI 工具并不支持交互式输入，因此需要一种机制来确保命令的可预测性。

- **智能 TTY 检测**：默认检测终端类型。在非 TTY 环境（如 AI Agent、CI/CD）中自动禁用交互，缺失参数时立即报错并给出提示，而不是挂起等待。
- **全局参数支持**：提供全局参数 `--no-interactive`（或通过环境变量 `CRATER_NO_INTERACTIVE`）。
- **设计一致性**：为了减少记忆负担，**所有命令**（即使本身没有交互逻辑）都应支持该全局参数，且不会报错。这允许 AI 或脚本编写者在所有调用中统一添加该标志，以确保绝对的非交互执行。

### json 原始输出格式

为了确保 AI Agent 能够稳定地解析 CLI 的输出，需要提供结构化的数据格式。

- **纯净 JSON 输出**：提供全局参数 `--json`。开启后，`stdout` 必须仅输出纯净的原始 JSON 数据，严禁包含任何描述性文字（如 "Here is the result:"），以确保 `jq` 或 AI 解析器的稳定性。
- **Stderr 职责分离**：所有的非数据消息（如警告、进度、本地化说明）必须输出到 `stderr`，确保不干扰 `stdout` 的解析逻辑。
- **隐式非交互**：开启 `--json` 时应自动激活 `--no-interactive`，防止 AI 因等待交互而挂起。
- **英文 Key 稳定性**：无论当前的本地化设置（i18n）为何，JSON 中的字段 Key 必须始终保持英文，确保代码逻辑的向后兼容。
- **源码驱动的错误码管理**：为了保证一致性，错误码常量定义直接维护在源码中。在分发阶段，AI 负责将这些定义总结并更新到 **Agent Skills** (`SKILL.md`)。这种方式避免了手动维护文档的滞后性，确保了 AI Agent 始终掌握最新的错误字典和自愈逻辑。

## 人文关怀

### 多语言支持

至少希望支持中文和英文，能允许用户安装后切换吗，还是需要发布不同语言的安装包？

- **单一二进制 + 运行时切换**：严禁发布多语言独立安装包，通过内嵌语言包实现单一分发。
- **优先级策略**：不提供 `--lang` 参数。语言切换优先级为 `持久化配置（crater config language）` > `环境变量 (CRATER_LANG)` > `系统默认 Locale`（自动检测）。
- **机器可读性约束**：无论显示语言为何，`--json` 等结构化输出必须保持英文 Key 和一致的结构，确保 AI Agent 的解析稳定性。

### Tab 命令补全

为 CLI 工具的人类使用者也提供比较好的使用体验。

这里的 “补全” 指 Shell Tab completion：用户在命令输入过程中按下 Tab，Shell 根据当前输入上下文给出候选项（并可能允许继续 Tab 在候选中选择）。

从体验上可以拆成三个层次（由浅入深）：

- **命令与子命令补全**：`crater <Tab>`、`crater auth <Tab>`，列出当前可用的子命令以及简介。
- **选项（flags）补全**：`crater auth ls -<Tab>`、`--pl<Tab>`，补全短选项与长选项。
- **选项取值的动态补全**：`crater auth switch -p <Tab>` 补全平台；`-u <Tab>` 补全用户名；候选项来自本地状态（如 `state.json`）并随登录上下文变化。

实现难点主要集中在第三层（动态补全）：

- **动态数据源边界**：补全发生在输入阶段且调用频繁，必须做到只读、快速、稳定。推荐只读取本地状态（如 `state.json`），避免任何网络请求；是否读取 keyring 需要非常谨慎，通常不建议将其纳入补全流程。
- **跨 Shell 兼容性**：bash/zsh/fish 的补全能力差异很大，尤其是 “候选项 + 描述” 展示与 “多次 Tab 菜单选择” 的交互体验并不一致。应接受不同 Shell 的自然差异，而非强行做成统一交互。
- **参数上下文解析**：为了知道当前是在补全 `-p` 的取值还是在补全命令，需要正确解析光标前的 tokens（含引号、空格、`--` 分隔符、重复 flags 等），这类边界情况很容易踩坑。
- **性能与健壮性**：补全逻辑应对状态文件不存在/损坏/无上下文时优雅退化（返回空候选），并严格处理转义，避免把包含空格或特殊字符的候选项补全坏。

推荐的落地方式（渐进式）：

- **先做基础补全**：优先使用 Cobra 的 completion 框架生成 bash/zsh/fish 的命令与 flags 补全，快速覆盖前两层体验。
- **再做少量动态值补全**：只考虑对少数关键 flags（如 `-p/-u/-m`）提供动态候选；补全时仅解析本地 `state.json`，不做网络请求；对不同 Shell 允许体验差异（zsh/fish 更接近“交互式选择”，bash 可用但更朴素）。
